Функциональные требования

1.1. Сбор и синхронизация данных
Система должна обеспечивать автоматический сбор данных о коммитах, репозиториях, ветках и пользователях при наступлении определённых событий (push, создание ветки и т.п.)
1.2. Хранение данных
Все собранные данные должны храниться в реляционной базе данных. 
1.3. API и бизнес-логика
Бэкенд-сервис должен предоставлять REST API с двумя основными контроллерами:
DataBaseController – для получения сырых данных по сущностям (репозитории, коммиты, пользователи).
CodeMetricsController – для получения агрегированных метрик продуктивности.
1.4. Визуализация и пользовательский интерфейс
Фронтенд-часть должна представлять собой интерактивный дашборд, отображающий аналитику по активности пользователей и репозиториев.
Интерфейс должен включать графики для визуализации метрик в реальном времени.
Дашборд должен обновлять данные при изменении в репозиториях без необходимости ручного обновления страницы. 
1.5. CI/CD и развертывание
В системе должна быть настроена непрерывная интеграция и доставка.
Пайплайн должен автоматически запускаться при коммитах в ветки dev, test и main.
Для каждого сервиса должны быть определены Dockerfile и docker-compose.yml, обеспечивающие контейнеризацию и оркестрацию компонентов (бэкенд, база данных, фронтенд, мониторинг и т.д.).
В процессе развертывания новый docker-образ должен доставляться на целевой сервер, после чего контейнеры перезапускаются через docker-compose.

Нефункциональные требования

2.1. Сбор и синхронизация данных
Сбор данных должен инициироваться через вебхуки Gitea. 
При получении события должен вызываться endpoint PostUpdateDatabase, который парсит payload и обновляет информацию в базе данных.
2.2. Хранение данных
Для хранения данных должна использоваться база данных PostgreSQL. 
Доступ к данным должен осуществляться через Entity Framework Core (ORM).
2.3. API и бизнес-логика
Для реализации бэкенд-сервиса должна использоваться ASP.NET Core 8.0. 
Фронтенд должен использовать HTTP-ответы от REST API бэкенда в формате JSON. 
API должно поддерживать HTTP-запросы в формате JSON и возвращать структурированные данные для фронтенда.
2.4. Визуализация и пользовательский интерфейс
Для реализации фронтона должны быть использованы Vue.js и TypeScript. 
Графики должны отображаться с помощью Chart.js. 
Обновление данных дашборда должно выполняться с помощью HTTP-запросов к API.
2.5. CI/CD и развертывание
Непрерывная интеграция и и доставка должны быть реализованы с использованием Drone CI/CD и Drone-Runner
2.6. Производительность
Время отклика REST API должно быть минимальным (целевое значение – менее 200 мс для типовых запросов при нормальной нагрузке).
Графики и дашборд должны отображаться с приемлемой интерактивностью, без заметных задержек при обновлении данных.
2.7. Надёжность и отказоустойчивость
Система должна быть устойчивой к сбоям отдельных компонентов. Контейнеры должны автоматически перезапускаться при падении (политика restart: unless-stopped в docker-compose).
Потеря данных при аварийном завершении работы базы данных должна быть минимизирована за счёт использования постоянных томов (Docker volumes) и регулярного резервного копирования (при необходимости).
2.8. Масштабируемость
Архитектура должна позволять горизонтальное масштабирование бэкенд-сервисов и базы данных при увеличении нагрузки (например, за счёт балансировки нагрузки и репликации PostgreSQL).
2.9. Безопасность
Доступ к веб-интерфейсу и API должен быть ограничен механизмами аутентификации (интеграция с Gitea OAuth или базовой HTTP-аутентификацией).
Передача данных между компонентами должна осуществляться по защищённым протоколам (HTTPS для внешних запросов).
Секреты (пароли базы данных, токены доступа) не должны храниться в открытом виде в коде или файлах конфигурации; должны использоваться переменные окружения или зашифрованные хранилища.
2.10. Удобство использования
Веб-интерфейс должен быть интуитивно понятным и не требовать специального обучения от пользователя.
Все ключевые метрики и графики должны сопровождаться подписями и пояснениями.
2.11. Мониторируемость и наблюдаемость
Система должна экспортировать метрики доступности и производительности (HTTP-статусы, время ответа, использование ресурсов) в VictoriaMetrics.
Должны быть настроены алерты (например, в Grafana) для критических состояний (недоступность сервиса, превышение порогов CPU/RAM).
2.12. Поддерживаемость
Кодовая база должна быть структурирована, соответствовать принятым стандартам оформления и содержать комментарии к сложным участкам.
Документация по развёртыванию и настройке системы должна быть актуальной и доступной для членов команды.
Используемые технологии должны быть актуальными (ASP.NET Core 8.0, Vue.js 3, PostgreSQL 14+ и т.д.) и иметь достаточную поддержку сообщества.
2.13. Совместимость
Система должна корректно взаимодействовать с Gitea версии не ниже 1.19 через вебхуки и API.
Все компоненты должны быть совместимы с Docker и docker-compose, обеспечивая одинаковое поведение в среде разработки, тестирования и на продакшене.
